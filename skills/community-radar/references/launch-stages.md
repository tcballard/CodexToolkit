# Stage-aware engagement

| Stage | Appropriate participation | Avoid |
|---|---|---|
| idea | learn vocabulary, answer from existing expertise, observe repeated problems | pitching an unbuilt solution as available |
| prototype | recruit narrowly for problem validation where rules permit; disclose limitations | broad launches, invented capability, urgency theater |
| alpha | invite qualified testers, publish technical learning, answer exact supported use cases | presenting unstable behavior as production-ready |
| beta | seek workflow feedback, respond to alternative requests, document constraints | repeated community launches without meaningful change |
| open source | help adjacent maintainers, answer implementation questions, improve docs, publish substantive releases | issue hijacking, drive-by links, maintainer spam |
| commercial | join buyer and practitioner conversations with transparent affiliation and usable evidence | disguised sales outreach or unsupported ROI claims |

When stages combine, apply the stricter truth and readiness boundary. `Open source alpha` permits transparent testing invitations but not a mature-tool launch posture.

## Readiness gates

Before recommending a product-linked action, verify:

- the named capability exists now;
- installation or access works for the intended audience;
- limitations relevant to the conversation are disclosed;
- the project has a credible destination page or repository front door;
- the participant can answer likely follow-up questions;
- the action complies with community rules.

If a gate fails, recommend the prerequisite and when to revisit the opportunity.
